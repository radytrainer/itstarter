# Database guide

PostgreSQL 17 is the single source of truth. Redis only ever holds copies that can be rebuilt.

- Schema (TypeScript): [apps/api/src/db/schema/](../apps/api/src/db/schema/)
- Migrations (SQL, generated, committed): [apps/api/drizzle/](../apps/api/drizzle/)
- Seed data: [apps/api/src/db/seed/](../apps/api/src/db/seed/)
- Entity diagram: [ARCHITECTURE.md §3](ARCHITECTURE.md#3-database-erd)

## Conventions

| Topic           | Rule                                                                                                                                   |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Primary keys    | UUIDv7 generated by the app (time-ordered). `gen_random_uuid()` is the SQL fallback. Lookup tables use small integers.                 |
| Timestamps      | `created_at`, `updated_at` (`timestamptz`) on every mutable table. `updated_at` is set by the app on every update.                     |
| Soft delete     | `deleted_at` on `users`, `courses`, `worlds`, `lessons`, `activities`, `cohorts`. Always filter `deleted_at IS NULL`.                  |
| Content status  | `draft` → `published` → `archived`. Students only ever see `published`.                                                                |
| Translated text | `jsonb` shaped `{ "en": "...", "km": "..." }`. English is required; Khmer falls back to English.                                       |
| Usernames       | Lowercase `a-z 0-9 . _ -`, 3–50 characters (DB check). Unique among non-deleted users, so a name can be reused after deletion.         |
| Enums           | PostgreSQL enums for small fixed sets (statuses, lesson steps, XP sources). Activity **types** are text so new ones need no migration. |
| Deleting        | Content uses `restrict` (soft-delete instead). Deleting a user cascades to their profile, sessions and progress.                       |

## Two rules that protect students

1. **Answers never go to the phone.** `activities.config` is _public_ and must never contain answers.
   Answers live in `questions.config` (e.g. `{ "answer": 25 }`) and `question_options.is_correct / match_key /
correct_order`, which the API strips before sending. A test checks every seeded activity for this.
2. **XP can't be earned twice.** `xp_transactions` has a unique key on `(student_id, source_type, source_id)`.
   The engine inserts with `ON CONFLICT DO NOTHING`, so resubmitting an answer can never add XP again.
   `students.xp_total` is a cached sum of this ledger.

## Everyday commands

```bash
npm run docker:deps      # start PostgreSQL + Redis
npm run db:migrate       # apply pending migrations
npm run db:seed          # create missing base data, sample lessons and accounts
```

Inside Docker (full stack):

```bash
npm run docker:migrate   # docker compose run --rm tools node apps/api/dist/migrate.js
npm run docker:seed      # docker compose run --rm tools node apps/api/dist/seed.js
```

## Changing the schema

1. Edit the TypeScript schema in `apps/api/src/db/schema/`.
2. `npm run db:generate -- --name short-description` writes a new SQL file to `apps/api/drizzle/`.
3. **Read the SQL.** Renames can appear as drop + add, which loses data. Edit the SQL by hand if needed.
4. `npm run db:migrate`, then `npm run test:integration`.
5. Commit the schema change and the migration together. CI fails if they don't match.

Never edit a migration that has already run in production. Add a new one instead.

## Seeding

The seed is **idempotent and non-destructive**: it only creates rows that are missing. It never overwrites
lessons an admin has edited, and never resets a password. It is safe to run on every deploy.

| Variable                | Development                   | Production                         |
| ----------------------- | ----------------------------- | ---------------------------------- |
| `SEED_ADMIN_PASSWORD`   | defaults to `Admin#2028dev`   | **required**, 12+ characters       |
| `SEED_ADMIN_USERNAME`   | `admin`                       | `admin` unless set                 |
| `SEED_DEMO_USERS`       | `true`                        | `false` unless set to `true`       |
| `SEED_TEACHER_PASSWORD` | defaults to `Teacher#2028dev` | required if demo users are enabled |
| `SEED_STUDENT_PASSWORD` | defaults to `Student#2028dev` | required if demo users are enabled |

Development accounts: `admin`, `teacher.demo`, `student.demo` (teacher and student are in
"Generation 2028 – Class A").

The seed creates all **90 lessons** across 6 worlds. Every lesson has the six steps in order
(welcome → learn → see → play → challenge → reward); play and challenge may appear more than once
(a mouse game before the questions, or a creative project after them).

Rewritten lessons: `LessonSeed.revision` / `lessons.seed_revision`. When a lesson's revision in the
seed is higher than in the database, the seed replaces its steps (old activities are archived, so
answers and XP history stay) — unless staff edited the lesson, its activities or questions in the
admin area (any audit-log entry), in which case their version is kept and only the revision number is
updated. The seed report shows `lessonsUpgraded` and `lessonsKeptAsEdited`.

Retired content: `RETIRED_WORLD_SLUGS` / `RETIRED_BADGE_CODES` in `seed/data/foundation.ts`. On a database
seeded earlier, the seed archives them (soft delete; progress and XP history stay) and puts the remaining
worlds back in order — this is how Brain Playground became Math Playground + Logic Playground. When the
seed adds or retires content it also bumps `content:version`, so a running server shows it straight away.

## Tests

`npm run test:integration` recreates a separate database named `<POSTGRES_DB>_test` (e.g. `itstarter_test`) on
every run, applies all migrations, and tests the schema, constraints, relationships and seed. Your development
data is never touched.
